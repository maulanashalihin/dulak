title: SQLite performance
description: The benchmark data behind Dulak's DB settings — why synchronous=NORMAL, and what to expect on Apple Silicon.
---

Dulak ships with WAL + `synchronous = NORMAL` + `busy_timeout = 5000` +
`foreign_keys = ON` in `src/server/db.ts`. This page documents why, with
numbers measured on the reference hardware (see
[Test environment](#test-environment) below).

## Test environment

- **Machine:** Apple MacBook Pro (M4)
- **CPU:** Apple M4, 10 cores
- **RAM:** 16 GiB unified memory
- **Disk:** internal NVMe (not HDD — fsync cost is ~10µs, not ~2.4ms)
- **OS:** macOS 15 (Darwin 25.5.0)
- **Runtime:** Bun 1.3.14
- **Date:** August 2026

Methodology:

- **Direct matrix:** 50K single-row inserts + 50K point reads per config,
  fresh DB file per config, `busy_timeout = 5000` fixed, only
  `journal_mode` / `synchronous` varied.
- **Full-stack:** Hono + `bun:sqlite`, concurrent load (50 workers), JSON
  responses, 5K–10K requests per endpoint. Same concurrency used for the
  Laravel comparison below.

## The settings

```ts
db.exec("PRAGMA journal_mode = WAL");
db.exec("PRAGMA synchronous = NORMAL"); // the one that matters for writes
db.exec("PRAGMA busy_timeout = 5000");
db.exec("PRAGMA foreign_keys = ON");
```

## Benchmark: pragma matrix

Direct `bun:sqlite` prepared statements (no HTTP), 50K single-row inserts +
50K point reads, fresh DB per config:

| Config | writes/s | reads/s |
| --- | ---: | ---: |
| `rollback journal` + `FULL` (SQLite default) | 3,508 | 244K |
| **WAL + `NORMAL`** | **94,813** | **526K** |
| WAL + `OFF` (unsafe) | 115,325 | 538K |

- **`NORMAL` is ~27× faster for writes** than the default `FULL` — that is
  the whole point. Reads more than double (+115%) because WAL eliminates
  the rollback-journal lock that serialises readers.
- `OFF` is another 22% on top but risks **database corruption** on power
  loss — never use it for real data.
- On HDD-based VPS hardware the write gap is even wider (~48×) because
  `FULL`-mode fsync costs ~2.4ms per commit vs ~10µs on NVMe. The ratio
  scales with disk latency; the conclusion is the same: `NORMAL` wins.

## Why WAL alone isn't enough

WAL fixes **read concurrency** (readers don't block the writer) but does
**not** remove the per-commit fsync — that is `synchronous`'s job. With the
SQLite default (`rollback journal` + `FULL`), every commit calls `fsync`
(~10µs on NVMe, ~2.4ms on HDD), and because `bun:sqlite` is synchronous,
commits serialize on the single event loop. `NORMAL` keeps WAL's crash
consistency but skips the per-commit fsync → ~95K writes/s on NVMe.

## Full-stack numbers

Through a real HTTP server (Hono + `bun:sqlite`, concurrent load, JSON
| Endpoint | req/s | p50 latency | p99 latency |
| --- | ---: | ---: | ---: |
| Point read (`GET /users/:id`) | 51,934 | 0.82ms | 2.89ms |
| List 20 rows (`GET /users?limit=20`) | 32,222 | 1.45ms | 3.09ms |
| Create (`POST /users`) | 19,614 | 1.82ms | 13.96ms |
| Update (`PUT /users/:id`) | 25,337 | 0.62ms | 3.28ms |
| Delete (`DELETE /users/:id`) | 27,744 | 1.41ms | 5.29ms |

The no-DB health check (63K) is only 17% faster than the DB point read
(52K) — not 10× faster as you might expect. That's because HTTP overhead
(connection handling, Hono routing, JSON serialization) costs ~16µs per
request, while the SQLite query itself adds only ~2µs. The database is so
fast that it's barely visible in the HTTP path.

The gap between direct (95K) and HTTP (20K) writes is request handling —
routing, JSON parsing, response serialization — which is ~5× the raw
commit cost. Reads drop ~10× (526K → 52K) because the per-request HTTP
overhead dominates a ~2µs query.

For context, the TCP kernel ceiling on this machine is ~180K req/s — the
point-read endpoint reaches 29% of that, with the rest being Hono routing
+ JSON serialization + SQLite overhead. Numbers are median of 3 solo runs
(no other server running during each test).

## Dulak vs Laravel (FrankenPHP)
Same machine, same SQLite (WAL + `NORMAL` + `busy_timeout = 5000`), same
CRUD endpoints, same concurrency (c=50). Laravel 13.24 on FrankenPHP
(8 workers) — the fastest production PHP server available for Laravel.
Each server benchmarked solo (no other server running). Median of 3 runs.

| Endpoint | Dulak (Hono+Bun) | Laravel (FrankenPHP) | Dulak faster |
| --- | ---: | ---: | ---: |
| `GET /health` (no DB) | 63,205 req/s | 6,169 req/s | 10.2× |
| `GET /users/:id` (PK read) | 51,934 req/s | 6,391 req/s | 8.1× |
| `GET /users?limit=20` (list) | 32,222 req/s | 4,734 req/s | 6.8× |
| `DELETE /users/:id` (delete) | 27,744 req/s | 5,655 req/s | 4.9× |
### Why the gap

**Reads (7–10×):** Laravel routes through kernel bootstrap → middleware
stack → Eloquent ORM (query builder → model hydration → collection) →
JSON serialization. Dulak uses Hono's zero-overhead router + raw prepared
statements + Bun's native JSON — no ORM, no model hydration, no collection
wrapping.

**DELETE (4.9×):** The fairest write comparison — no password hashing on
either side. The gap is pure framework overhead: Eloquent model lookup +
delete + event dispatch vs a single prepared statement.

POST/PUT are excluded from the comparison table because Laravel's
argon2id password hashing (~240ms/op) dominates the request time, making
throughput numbers reflect hashing speed rather than framework overhead.
Without hashing, Laravel writes would be ~5–6K req/s (extrapolated from
DELETE), still 4–5× slower than Dulak.

### Laravel setup notes

| Server | req/s (health) | Notes |
| --- | ---: | --- |
| `artisan serve` (single-worker) | ~500 | PHP dev server, not production |
| RoadRunner (Octane, 4 workers) | ~8,400 | Crashed under c>5 with SQLite |
| **FrankenPHP (Octane, 8 workers)** | **6,169** | Best stable result |
FrankenPHP was the only PHP server that stayed up under concurrent load
with SQLite. RoadRunner crashed repeatedly at concurrency >5 — likely
SQLite WAL lock contention not handled gracefully. `artisan serve` is
single-threaded and not representative of production.

## Transactional writes

When inserts are batched inside a single `db.transaction()`, the per-commit
fsync fires once at the end instead of per row:

| Mode | writes/s | µs/row |
| --- | ---: | ---: |
| Autocommit (one fsync per row) | 94,813 | 10.5 |
| **Single transaction** | **1,329,836** | **0.75** |

That is **14× faster** — 1.3M inserts/s. Always batch bulk writes in a
transaction; the `db.transaction()` helper is built for this.

## The tradeoff

| Mode | Power-loss behavior | Writes/s |
| --- | --- | ---: |
| `NORMAL` | last WAL transactions may be lost; **DB never corrupts** | ~95K |
| `FULL` | zero loss | ~3.5K |

`NORMAL` is the right default for web apps. Switch to `FULL` only for
data where losing the last few transactions is unacceptable (financial
records, etc.). Numbers vary by hardware — re-run the matrix on your own
machine before tuning further.
