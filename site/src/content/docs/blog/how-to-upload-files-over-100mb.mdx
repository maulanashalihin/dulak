A 2GB video upload over a plain multipart form will fail. Not maybe — it will fail, usually at 90%, and the user starts over. The reasons are structural: a dropped connection kills the whole request, proxies cap body sizes, and one long request can time out.

The fix is chunking: split the file, upload piece by piece, track progress, resume where you left off. The [tus protocol](https://tus.io/protocols/resumable-upload) does exactly this, and Bun has a spec-compliant implementation you can use as-is.

This tutorial walks through the whole thing — server, client, resume, progress — on Dulak.

## Step 1: server — tus endpoints

Dulak ships tus at `/uploads` out of the box: creation, resume (HEAD), chunked append (PATCH), termination, checksums. Auth and ownership are enforced on every endpoint. There is nothing to install — it's three flat modules, zero dependencies.

```bash
# already enabled — nothing to configure
curl -X OPTIONS http://localhost:4000/uploads
```

The server returns tus capabilities. Uploads land in `UPLOAD_DIR` (default `./data/uploads`), with one SQLite row per upload tracking offset, length, and owner.

**If you're not on Dulak:** any tus server works — `tus-node-server`, `tusd`, or a cloud variant. The client code below is protocol-standard and works against any of them.

## Step 2: client — upload with tus-js-client

Install the client library and upload the file:

```bash
bun add tus-js-client
```

```ts
import { Upload } from "tus-js-client";

const file = input.files[0]; // from <input type="file">

const upload = new Upload(file, {
  endpoint: "/uploads",
  chunkSize: 5 * 1024 * 1024,        // 5MB per request
  retryDelays: [0, 3000, 5000, 10000, 20000],
  metadata: {
    filename: file.name,
    filetype: file.type,
  },
  onError: (err) => console.error("Upload failed:", err),
  onProgress: (bytesSent, bytesTotal) => {
    const pct = Math.round((bytesSent / bytesTotal) * 100);
    console.log(`Uploaded ${pct}%`);
  },
  onSuccess: () => console.log("Done:", upload.url),
});

upload.start();
```

That's a working upload. Chunking is handled for you — each PATCH is a small, proxy-safe request.

### Why 5MB chunks?

Two constraints meet here:

- **Proxy limits.** [Cloudflare caps request bodies at 100MB](/uploads/tus/) — a single request over that is rejected at the edge. Chunks must stay well under it.
- **Failure cost.** A dropped connection re-sends only the in-flight chunk. 5MB is small enough that the retry is cheap, large enough that HTTP overhead per chunk stays negligible.

Anything from 1MB to 10MB works; 5MB is a sane default.

## Step 3: resume after interruption

This is the whole point of tus. When the connection drops, the upload doesn't die — it stops, and you can continue.

```ts
// On failure, remember where the upload was so we can resume later.
onError: (err) => {
  // upload.url is the server's Location — keep it in localStorage
  localStorage.setItem(`upload:${file.name}`, upload.url);
},
```

```ts
// On the next page load, if the same file is picked again:
const resumeUrl = localStorage.getItem(`upload:${file.name}`);
if (resumeUrl) {
  const upload = new Upload(file, {
    endpoint: "/uploads",
    uploadUrl: resumeUrl,        // resume from the saved URL
    chunkSize: 5 * 1024 * 1024,
    // ... same callbacks
  });
  upload.start();
}
```

`tus-js-client` handles the HEAD request internally — it asks the server "where did you stop?" and continues from that offset. No restart, no lost progress.

## Step 4: progress that survives reloads

The progress bar is easy; making it survive a refresh is the useful part. Combine Step 3 with the progress callback:

```ts
onProgress: (bytesSent, bytesTotal) => {
  localStorage.setItem(`upload:${file.name}:progress`, String(bytesSent));
  // update UI: bytesSent / bytesTotal
},
```

On resume, the client re-reads the offset from the server (via HEAD), so the bar snaps to the true position even if the page reloaded.

## Step 5: verify with network throttling

Test the resume path before shipping — it's the part that's easy to get wrong:

1. Open DevTools → Network → throttling, pick "Slow 3G"
2. Start uploading a 200MB file
3. Kill the connection mid-upload (toggle to Offline)
4. Re-enable the network, resume
5. Confirm the upload continues from where it stopped, not from zero

If it restarts, the server offset and the client's saved URL don't match — check that `uploadUrl` is being persisted and passed back correctly.

## When you don't need any of this

If your files are under ~100MB and the connection is reliable, a plain multipart form is simpler and correct:

```ts
const form = await c.req.formData();
const file = form.get("file");
await Bun.write(`${config.upload.dir}/${file.name}`, file);
```

Ten lines, no client library, no protocol. The [form data guide](/uploads/form-data/) covers it. Use tus only when the file is big enough that a failed upload costs real time — that's the ~100MB line.

## The short version

**Small files: form data. Files over ~100MB: tus.**

Server: shipped in Dulak at `/uploads` — nothing to install. Client: `tus-js-client`, five lines of config. Resume: save `upload.url`, pass it back as `uploadUrl`. Progress: `onProgress` callback, persisted in `localStorage`. Test with network throttling before you trust it. The [tus docs](/uploads/tus/) have the full protocol and configuration reference.
