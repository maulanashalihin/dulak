Dulak was designed for AI agents. `AGENTS.md` at the repo root tells the
agent where everything lives, so it can build features without guessing
the conventions. Your job is not to write code or remember syntax — it's
to describe what you need and review what the agent produces.

<aside>
**This workflow is opinionated.** It's what works for the Dulak author,
not a universal law. Treat this page as a starting point and feel free
to develop your own workflow. The conventions in `AGENTS.md` are the
hard rules; everything on this page is a suggestion.
</aside>

<aside>
**Personally recommended: [omp.sh](https://omp.sh).** It reads
`AGENTS.md` automatically, runs in your terminal, and can drive a real
browser to verify UI changes. The workflow below works with omp.sh,
Claude Code, Cursor, opencode, Windsurf, or any agent that can read
files and run shell commands.
</aside>

## The workflow at a glance

```
1. Scaffold        bun create dulak@latest my-app
2. Plan            write PLAN.md — the story of your needs
3. Loop            prompt → agent implements → you review → commit
4. Ship            agent verifies everything is green
```

## Plan: write the story of your needs

Before the agent writes any code, write a `PLAN.md` in the project root.
This is not a technical spec — it's the **story of what you need**.
Describe it in plain language, like you're explaining to a friend:

- **What is it?** — "A bookmark manager where users save links and
  organize them with tags."
- **Who uses it?** — "Authenticated users. No public pages except login
  and register."
- **What does it do?** — "Users can save a link with a title and tags,
  view all saved links sorted by newest, and filter by tag."

Don't mention pages, routes, database tables, or code — the agent
figures out all of that itself. It knows the conventions from
`AGENTS.md`; your job is to describe the need, not the implementation.

```markdown
# Bookmark Manager

A simple app where authenticated users save and organize links.

## Design

See `design/bookmarks-mockup.png` for the layout.

## Behavior

- Adding a bookmark: user pastes a URL, types a title, picks tags. On
  submit, the bookmark appears at the top of the list.
- Filtering by tag: clicking a tag narrows the list to bookmarks with
  that tag. Clicking "All" resets the filter.
- No public pages. Everything behind login.
```

### Attach a design

If you have a visual design — a mockup from ChatGPT, a Figma export, a
hand-drawn sketch — put it in the project and reference it from the
plan. The design carries what words can't: colors, spacing, layout.

Two ways to provide it:

- **Image** (`design/mockup.png`) — the agent reads it and matches the
  design. Requires the agent's model to support image input.
- **HTML mockup** (`design/mockup.html`) — a single static page with
  real markup and CSS, generated in ChatGPT or Gemini Canvas. Works even
  when the agent can't read images, because the structure is in the
  markup itself.

Either way, reference it from the plan and let the agent work from it:

```markdown
## Design

See `design/bookmarks-mockup.html` for the layout — match its
structure, spacing, and colors.
```

### Review the plan

Read it back. Does it describe what you need? Would a non-technical
friend understand it? If it reads like code, it's too technical —
rewrite it in plain language. Once it reads like a story, hand it to the
agent.

## The workflow loop

```
prompt → agent implements → you review → commit
```

### Step 1: Prompt

Give the agent the plan and let it work. Work through it one slice at a
time — not the whole app in one prompt:

> Read PLAN.md and build the bookmark manager. Start with saving and
> listing bookmarks, then show me what you did.

The agent reads the plan, follows `AGENTS.md`, writes the code, the
tests, and the migrations. Don't tell it how — it knows.

### Step 2: Review

The agent verifies its own work — typecheck, tests, browser console —
and reports back. Your job is to read the report and judge the result:

- Does the app do what the plan describes?
- Does it look like the design?
- Does the agent's report show everything passing?

Open the app and look. If something's off, tell the agent — in any
words. The agent reasons about what you mean and finds the cause:

> The form doesn't save. After submitting, the bookmark doesn't appear
> in the list.

There's no wrong way to describe a problem. Say it as you'd say it to a
friend; the agent handles the debugging.

### Step 3: Commit

Once the slice works, have the agent commit it:

> Commit this slice.

Commit after each verified slice — it's a checkpoint you can roll back
to. A plan with several slices produces several commits.

## The plan evolves

As you build, you'll realize the plan missed something — a field, a
behavior, a page. Update `PLAN.md` first, then tell the agent:

> I updated PLAN.md — bookmarks now also show the domain. Continue from
> where you left off.

The plan stays the source of truth. Update it, and the agent follows
the update.
