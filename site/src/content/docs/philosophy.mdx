---
title: Philosophy
description: Why Dulak is deliberately boring.
---

**Dulak** is the Banjar word for *bored* — the name is the philosophy. Every
choice in this starter favors the next maintainer, human or AI agent, over
cleverness. This page is the reasoning behind the rules you'll see codified
in `AGENTS.md` and the [Conventions](/architecture/conventions/) page.

## Deliberately boring

The strongest tool a codebase has is predictability. Dulak would rather be
unremarkable and understandable than clever and surprising. If a piece of
the starter can't be explained in one sentence, it doesn't belong here.

## Zero-dependency where it's cheap

Dependencies are a liability. Vanilla CSS by default (Tailwind v4 available
as a template), a hand-rolled rate limiter and OAuth client instead of
packages that pin the stack, raw `bun:sqlite` instead of an ORM. When a
60-line module does the job, it ships — and it can be read, audited, and
forked without a license review.

## One obvious way to do things

A single structural convention, codified in `AGENTS.md`: routes in
`routes/<feature>.routes.ts` with handlers inline, shared logic as flat
modules, all SQL in `db.ts`, schema in versioned migrations. No feature
folders, no second way to do the same thing. New contributors — and AI
agents — are never left to invent a convention.

## Discoverability as a contract

Given any URL you can derive the file that owns it: `src/server/routes/`
mirrors URL namespaces, every URL lives in exactly one file (GET renders
and POST actions together), and new features get their own
`<feature>.routes.ts`. Pasting a broken route into the codebase leads to
exactly one file.

## Production-shaped, not production

The guardrails a deployed app needs — migrations, CSRF, rate limiting,
security headers, session rotation, graceful shutdown, CI, Docker — are
wired from day one, so you start with a skeleton *shaped* like a production
app. But it is not one: the only pre-built feature is auth, and anything
deployment-specific (Redis-backed rate limiting, CDN, observability) is a
documented swap point. The product is yours to add by following the
conventions.

## Boring versions, current versions

Hono 4.x, Bun 1.3, Inertia v3 — current stable releases, nothing pinned to
an experimental track. Upgrades are deliberate decisions, not defaults —
the previous HTTP layer was swapped for Hono precisely to avoid a
rewrite-track dependency (Elysia 2 beta).

## Correctness over cleverness

Synchronous, explicitly typed, parameterized queries; fail-fast config;
deterministic tests (`bun test --isolate`). Trade the clever trick for the
boring one that's obviously right.

## Built for AI agents too

The "next maintainer" includes the agent writing the next feature: TypeBox
schemas with exact error shapes, strict TypeScript
(`strict` + `noUncheckedIndexedAccess`) so mistakes fail at compile time,
conventions codified where agents read them, and a deterministic test
suite as the safety net. A codebase that's easy for an agent to extend
without hallucinating conventions is a codebase that stays coherent.
