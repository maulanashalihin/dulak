# README.md

## Summary

This README describes a production-shaped full-stack boilerplate built on Bun, pairing Elysia (HTTP framework), bun:sqlite (database), and Inertia v3 / React 19 (server-driven UI with in-process SSR). It wires auth (register/login/logout, forgot/reset password, Google OAuth), user/admin roles, rate limiting, a 20-test E2E suite, and Docker end to end, entirely within a single Bun process.

The stack's architecture is organized into a server layer (app composition, validated env config, bun:sqlite access, migration runner, argon2id auth with DB-backed sessions, an Inertia v3 server adapter, mail drivers, rate limiter, logger, security, and assets pipeline) plus a client layer (Inertia bootstrap, in-process SSR renderer, explicit page registry, React pages and components) and shared types. Key mechanics include a request lifecycle of correlation-id logging, CSRF origin check, session resolve and guards, Inertia rendering (SSR HTML for browsers, JSON for XHR), and 422/404/500 error handling.

Notable implementation decisions are documented: Elysia 1.4 quirks (hook ordering, plugins dropping hooks, hand-rolled rate limiter), removal of import.meta.glob from Bun 1.3 (explicit page imports), CSP using script-src 'unsafe-inline' because Inertia embeds page payloads as inline JSON, versioned SQL migrations applied at startup in transactions, and three mail drivers (log, resend, mailtrap). Deployment is via multi-stage Docker (oven/bun:1.3-alpine), with alternatives of bun build --compile for a single binary or bun run start behind a process supervisor.

## Key Takeaways

- The boilerplate runs entirely on Bun: Elysia (HTTP) + bun:sqlite (DB) + Inertia v3 / React 19 (SSR + hydration), with auth, roles, rate limiting, tests, and Docker wired end to end.
- Auth uses argon2id passwords via Bun.password, 256-bit random session tokens stored in SQLite, httpOnly SameSite=Lax cookies with 30-day expiry, and CSRF via Origin check.
- Inertia v3 is implemented with a server adapter that renders SSR HTML for browser visits, JSON for X-Inertia XHR, 409 + X-Inertia-Location on asset-version mismatch, partial reloads, one-shot flash, and shared props.
- Migrations are versioned SQL files applied at startup in filename order, each in a transaction, recorded in schema_migrations, and never re-applied; editing an applied migration is forbidden.
- Rate limiting is an in-memory fixed-window limiter keyed by X-Forwarded-For/peer IP on auth endpoints, swappable for Redis behind the same hook signature.
- Several Elysia 1.4 and Bun 1.3 quirks were handled: global onError hook ordering, plugins dropping hooks, hand-rolled rate limiter, and explicit page imports instead of import.meta.glob.
- Three mail drivers exist: log (default, testable), resend, and mailtrap (with optional sandbox inbox endpoint).
- Testing boots the full app against an in-memory SQLite DB and drives it via app.handle(), covering auth, guards/roles, reset flow, Inertia protocol, CSRF, and /health.

## Notable Quotes

> Never edit an applied migration — add a new numbered file instead.

> CSP uses `script-src 'unsafe-inline'` because Inertia embeds the page payload as inline JSON; external script injection is still blocked.

> X-Forwarded-For is trusted for rate limiting — only run behind a proxy that sets it.

## Contradictions

⚠️ **Contradiction**: CSP uses script-src 'unsafe-inline' (weaker than ideal CSP guidance) as a deliberate trade-off required by Inertia embedding page payloads as inline JSON.
⚠️ **Contradiction**: X-Forwarded-For is trusted for rate limiting, which is generally insecure unless running behind a trusted proxy that sets it — the README itself calls this caveat out.
